1. Fractal Wrongness (Refined Definition)

Informally (after Keunwoo Lee): a position is fractally wrong when the wrongness is self-similar at every scale. Zoom into any supporting argument and that's also wrong, and the arguments supporting that are wrong, all the way down.

Formally:

Let C be a claim with supporting structure S(C) = {s₁, s₂, ..., sₙ}
where each sᵢ is itself a claim with its own structure S(sᵢ).

A claim C is FRACTALLY WRONG if:
  1. C is false
  2. For every sᵢ in S(C), sᵢ is false
  3. For every sᵢ in S(C), sᵢ is itself fractally wrong

This is a recursive definition. The base case is reached when a
claim has no supporting structure (a brute assertion) and that
assertion is false.

Consequence: a single falsified base-claim collapses the entire
structure. This is the Popperian insight that makes fractal
wrongness fixable.

The practical implication: you do not need to audit every floor of a wrong tower. You need to find one load-bearing claim at the base and test it. If the foundation crumbles, the structure falls with it.

This is why falsifiability (Popper 1959) is the master tool against fractal wrongness: it turns an intractable verification problem into a tractable refutation problem.

2. The Worked Example: A Fractally Wrong Bug

A production incident from a hypothetical fintech team. Names redacted. Pattern real.

The Claim Tower

C₀: "Our payment reconciliation is correct"
 ∟ s₁: "The AI-generated reconciler passes all tests"
     ∟ s₁.₁: "The tests cover all edge cases"
         ∟ s₁.₁.₁: "The AI wrote the tests from the spec"
             ∟ s₁.₁.₁.₁: "The spec is the source of truth"
 ∟ s₂: "CI has been green for six weeks"
     ∟ s₂.₁: "Nobody has reported a discrepancy"
         ∟ s₂.₁.₁: "Customers would complain if money was missing"
             ∟ s₂.₁.₁.₁: "Our customers reconcile their own ledgers"

The Ground Truth (Discovered At 3am)

The reconciler silently drops rows where the currency field is null.
Null currency happens ~0.01% of the time (internal transfers only).
The affected amounts sum to $47,000/month.

Let us audit the tower:

s₁.₁.₁.₁: "The spec is the source of truth"     ❌
    The spec didn't mention null currency at all.
    The AI had nothing to test against.

s₁.₁.₁: "The AI wrote the tests from the spec"      ❌
    True literally. False operationally. The AI wrote
    tests for what the spec described. The tests inherit
    the spec's silence on nulls.

s₁.₁: "The tests cover all edge cases"              ❌
    They cover every case the spec named. The spec named
    none of the edge cases.

s₁: "The AI-generated reconciler passes all tests" ❌
    Passes tests that were never going to fail.

s₂.₁.₁.₁: "Customers reconcile their own ledgers"  ❌
    Two do. Eleven do not. The eleven trust our numbers.

s₂.₁.₁: "Customers would complain"                   ❌
    They can only complain about what they can see.
    They cannot see silent drops.

s₂.₁: "Nobody has reported a discrepancy"              ❌
    True. Misleading. See above.

s₂: "CI has been green for six weeks"                  ❌
    True and useless. CI runs the tests. The tests
    pass. The money is still gone.

C₀: "Our payment reconciliation is correct"             ❌
    $282,000 missing over six weeks.

The Popperian Base-Test

How long would it have taken to catch this? Let's trace the path:

Pick ONE falsifiable base claim: s₁.₁.₁.₁
"The spec is the source of truth."

Falsification test: find any production transaction shape
the spec does not mention.

Query: SELECT DISTINCT currency FROM transactions;
Time to execute: 12 seconds.
Result: NULL (47 rows), USD (2.1M rows), EUR (340K rows),
        GBP (180K rows), JPY (90K rows).

Does the spec mention NULL currency? No.
s₁.₁.₁.₁ falsified. Tower collapses.

Total time investment: under 30 seconds.
Investment if the team had started by testing the base: 30 seconds.
Investment without the base-test: 6 weeks + $282,000 + incident review.

This is the pattern. Not every bug is fractally wrong. But when one is, the cost of structural verification grows exponentially while the cost of base falsification stays constant.

3. Detection Criteria (Measurable)

An 8-point checklist for detecting fractal wrongness in code reviews, architectural proposals, PR descriptions, and incident postmortems. Each item scored 0 (absent) or 1 (present). Total score indicates likelihood of fractal wrongness.

CHECKLIST                                                    Score
□ 1. The claim has no stated falsification condition       __ / 1
□ 2. Supporting evidence is structural, not empirical      __ / 1
□ 3. Tests verify behavior not bounded by the spec         __ / 1
□ 4. Green CI is cited as sufficient evidence              __ / 1
□ 5. Assumptions are implicit, not enumerated              __ / 1
□ 6. No worked failure mode has been discussed             __ / 1
□ 7. Validation is social ("we all agreed") not empirical   __ / 1
□ 8. The proposal has zero adversarial review              __ / 1

SCORE INTERPRETATION:
  0-2  : Probably fine. No urgent action.
  3-4  : Warning. Request one base-test before proceeding.
  5-6  : Alert. Require falsifiable base claim + test.
  7-8  : Halt. Do not merge. Run Ritual 3 + Ritual 5 before resuming.

THRESHOLD RULE: if any single item would require more than 4 hours
of work to resolve, escalate to a Master-tier reviewer.

The checklist is deliberately binary. Weighted scoring invites rationalization. Binary scoring forces the reviewer to commit.

Usage in PR Reviews

Paste the checklist into a PR comment. Score each item. Post the total. If the score is 3 or higher, request the corresponding ritual before approving.

Usage in Postmortems

Retroactively score the failed system. A postmortem that reveals a score ≥5 indicates fractal wrongness was the root cause, not the surface bug. The fix is structural (better review process), not tactical (patch the specific bug).

4. AI Ritual 3: Ask For The Failure Mode

The v1 paper cited this ritual. v2 defines it in full.

The Ritual

NAME:       Ask For The Failure Mode
NUMBER:     3 (of the Ten AI Rituals)
TRIGGER:    Before accepting any AI-generated solution
PURPOSE:    Shift the interaction from affirmation to examination

PROCEDURE:
  1. The AI has proposed a solution S to problem P.
  2. Before accepting S, the human asks:
     "How could S fail?"
  3. The AI must enumerate at least three concrete failure modes.
  4. For each failure mode Fᵢ, the human asks:
     "What would we observe if Fᵢ were occurring?"
  5. The human verifies that at least one observation is
     practically measurable before accepting S.
  6. If no measurable observation exists, S is a brute assertion
     and must be rejected (or demoted to hypothesis).

RATIONALE:
  AI systems trained on RLHF are biased toward producing the happy
  path. The training signal rewards affirmation. Asking for failure
  modes inverts the frame and engages the model in adversarial
  self-examination. This is the engineering equivalent of Popper's
  falsification criterion (1959).

FAILURE MODE OF THIS RITUAL:
  The AI may generate plausible-sounding but unfalsifiable failure
  modes ("it could fail if the cosmic rays align"). Counter-ritual:
  require each failure mode to have a concrete observable indicator
  that can be tested in production.

Example Application

Human: The AI suggests using exponential backoff for the retry loop.
Ritual 3: How could exponential backoff fail here?

AI response (good):
  1. Clock skew between retry attempts could invert the backoff order.
     Observable: retries arriving in unexpected sequence in the logs.
  2. The upstream service could return 200 OK while still rate-limiting
     us, causing us to stop backing off when we should continue.
     Observable: success rate < expected rate at nominal QPS.
  3. A client-side cache could mask failures, so retries never execute.
     Observable: retry counter never increments.

AI response (bad):
  1. It could fail if the universe is deterministic.
  2. It could fail if we have bad luck.
  3. It could fail if the specification is wrong.

The first response is actionable. The second is brute assertion.
Reject the second. Demand the first.

5. AI Ritual 5: Force Explicit Assumptions

The v1 paper cited this ritual. v2 defines it in full.

The Ritual

NAME:       Force Explicit Assumptions
NUMBER:     5 (of the Ten AI Rituals)
TRIGGER:    Whenever the AI proceeds with partial information
PURPOSE:    Surface hidden assumptions before they contaminate output

PROCEDURE:
  1. Before the AI generates a solution, ask:
     "List every assumption you are making about this problem."
  2. The AI must produce a numbered list of assumptions, each
     phrased as a falsifiable claim.
  3. The human reviews the list and marks each assumption:
     ✅ CONFIRMED       (human has verified the assumption)
     ❌ REJECTED       (assumption is false; restart)
     ⚠️ UNVERIFIED     (assumption might be false; flag)
  4. If any assumption is UNVERIFIED and load-bearing, the AI must
     restate the solution with that assumption as an explicit
     precondition.
  5. The solution is only accepted with all assumptions either
     CONFIRMED or explicitly flagged as preconditions.

RATIONALE:
  Fractal wrongness begins where assumptions are implicit. An
  AI that makes five hidden assumptions produces a solution
  whose wrongness can be self-similar at every level of that
  assumption stack. Making assumptions explicit is the single
  highest-leverage intervention against fractal wrongness.

FAILURE MODE OF THIS RITUAL:
  The AI may produce an incomplete list of assumptions, stating
  only the ones it recognizes. Counter-ritual: after the AI
  lists its assumptions, ask a second prompt:
    "What assumptions are you making that you did not list?"
  Repeat until the AI produces an empty list, or until the
  human is satisfied that major assumptions are covered.

Example Application

Human: Refactor this function to be thread-safe.
Ritual 5: List every assumption you are making.

AI response:
  1. The current single-threaded implementation is correct.
     Status: CONFIRMED (verified via unit tests).
  2. The caller is prepared to handle lock contention.
     Status: UNVERIFIED — caller is a tight loop in the hot path.
  3. The shared state can be safely wrapped in a mutex.
     Status: REJECTED — one field is a file handle that cannot
     be shared across threads without dup().
  4. "Thread-safe" means mutex-protected, not lock-free.
     Status: UNVERIFIED — caller didn't specify.

Action: do not proceed with the refactor. Return to the caller
with assumptions 2 and 4 as explicit questions. Reject the
mutex-based approach outright (assumption 3).

This saved: a week of debugging a file handle race condition.

6. The Scheherazade Loop (Formalized)

The v1 paper coined “Scheherazade Loop in human form” but did not define it precisely. v2 makes it testable.

Definition

A SCHEHERAZADE LOOP is a feedback pattern in which plausible
reasoning extends indefinitely because:
  1. Each step is locally coherent (sounds right)
  2. Each step defers verification to the next step
  3. The verification never arrives because the next step
     defers it again
  4. The loop sustains itself by social momentum, not empirical
     grounding

The name: Scheherazade told stories each night to delay her
execution. The king was kept engaged by the narrative, never
reaching the end. Our software version: the team is kept
engaged by the reasoning, never reaching the test.

Detection Pattern

Symptoms:
  · A 45-minute meeting discussing an implementation without
    anyone opening the code
  · A design doc with no "How do we verify this?" section
  · A proposal that has survived three review cycles without
    anyone running it
  · Phrases like "in principle", "conceptually", "basically"
    doing most of the load-bearing work
  · A long Slack thread that ends with "sounds good" and no
    action items

Measurement:
  Scheherazade coefficient = (minutes of discussion) / (minutes of execution)

  coefficient < 1    : healthy (more doing than talking)
  coefficient 1-5    : acceptable (normal design work)
  coefficient 5-20   : warning (Scheherazade suspected)
  coefficient > 20   : alert (Scheherazade confirmed)

Structural Prevention

Rule 1: Every design meeting must end with a concrete test
        that can be run in the next 24 hours.

Rule 2: Every review cycle must include at least one "has
        anyone actually run this?" question.

Rule 3: Every design doc must have a section titled
        "Falsification" with at least one concrete base-test.

Rule 4: If a proposal has survived review without execution,
        the next reviewer has the explicit authority to
        demand a 30-second base-test before further discussion.

Rule 5: The word "basically" is a reviewable event. Use it
        three times in a meeting and a facilitator calls
        Ritual 5 (Force Explicit Assumptions).

7. The Popperian Base-Test Protocol

A reproducible workflow any team can run today. Implemented as a slash-command style procedure.

/base-test [claim]

STEP 1: IDENTIFY
  State the claim C in one sentence.
  If it takes more than one sentence, the claim is not
  specific enough to test. Narrow it.

STEP 2: DECOMPOSE
  List the 3-5 load-bearing sub-claims supporting C.
  Each sub-claim must be itself a single sentence.

STEP 3: SELECT
  Choose the sub-claim that, if false, would most
  damage the overall claim. This is the BASE.

STEP 4: FALSIFY
  Design a test that would show the base to be false.
  The test must be:
    · concrete (specific query, specific measurement)
    · cheap (< 1 hour of work)
    · boolean (pass or fail, no gradients)
    · observable (produces evidence anyone can check)

STEP 5: EXECUTE
  Run the test. Do not discuss. Do not revise the test.
  Execute.

STEP 6: RECORD
  Write down the result. If the base is falsified,
  the entire claim structure is suspect. Restart.
  If the base holds, proceed to the next sub-claim.

STEP 7: REPEAT
  Work through the sub-claims in order of criticality.
  Stop when every load-bearing claim has survived a
  falsification attempt.

STEP 8: DOCUMENT
  Record the tests in a falsification log attached to
  the claim. Future reviewers reference this log.

Example Run (30 Seconds)

Claim: "Our payment reconciliation is correct."

Decompose:
  a. The spec is complete
  b. The tests cover the spec
  c. The production data matches the spec

Select: (a) is load-bearing for everything else.

Falsify: query distinct currencies in production.

Execute: SELECT DISTINCT currency FROM transactions;
         Result: NULL, USD, EUR, GBP, JPY

Record: spec does not mention NULL. (a) is falsified.

Restart: the entire tower is suspect. Investigate.

Total time: under 30 seconds.
Total cost: priceless.

8. Integration With 12-Ring Quality Gates

Fractal wrongness is a pattern that appears at every level of the quality gate stack. Each ring catches a different layer of fractal wrongness.

Ring → Level of fractal wrongness it catches
─────────────────────────────────────────────

● R0 GROUND
  Catches: brute non-claims (empty, bot-slop)
  Fractal level: the zero case

〜 R1 SIGNAL
  Catches: claims with no content (pure form, no substance)
  Fractal level: surface rhetoric

┃ R2 GATE (charter)
  Catches: claims that violate stated principles
  Fractal level: the value layer

♡ R3 AFFECT
  Catches: claims built on social pressure (sycophancy loop)
  Fractal level: validation-by-agreement

△ R4 FORGE
  Catches: claims that fail technical verification
  Fractal level: the testable layer — this is where
  the base-test protocol lives

◐ R5 IDENTITY
  Catches: impersonation, unearned authority claims
  Fractal level: source of the claim

◯ R6 OBSERVER
  Catches: meta-wrongness — the claim that the
  review system itself is free of fractal wrongness
  Fractal level: the review of reviews

⟡ M0 AETHER
  Catches: RFC-level hypothesis wrongness
  Fractal level: premise structure

⬡ M1 FLUX
  Catches: refactor proposals that would propagate
  fractal wrongness across the codebase
  Fractal level: change vectors

⟐ M2 VOID
  Catches: dead code whose deletion would reveal
  fractal wrongness in the remaining structure
  Fractal level: negative space

✦ M3 NEXUS
  Catches: cross-project wrongness (our fractal tower
  sits on their fractal tower)
  Fractal level: transitive dependency

✻ M4 OMEGA
  Catches: final sign-off where the entire claim
  structure has been verified at every ring
  Fractal level: the whole

The Scheherazade Loop lives primarily in the space between R3 (social validation) and R4 (technical verification). It survives because R3 says “everyone agrees” and R4 was never actually engaged. The base-test protocol forces the R3 → R4 transition.

9. Case Studies

Case 1: Aviation Checklists (Gawande 2009)

The aviation industry converged on checklists because post-incident reviews repeatedly found fractal wrongness: the pilot believed the aircraft was ready, the copilot believed the pilot had checked, the ground crew believed someone else had verified the fuel load. Each layer relied on the next without grounding in empirical check. Checklists are a structural antidote: they force a base-test at every layer.

Lesson: when human memory is the base-test, the base is corruptible by social pressure. Externalize the base to a checklist.

Case 2: Differential Diagnosis in Medicine

A patient presents with chest pain. A fractally wrong diagnostic process would be: “Most chest pain is anxiety. This patient is anxious. Therefore this is anxiety.” Each step sounds reasonable. The tower is fractally wrong because it never tests the base claim against alternatives.

The antidote is the differential diagnosis ritual: enumerate every possible cause, rank by prior probability, test the top candidates in order of severity-weighted probability. This is the medical equivalent of Ritual 5 (Force Explicit Assumptions) + Ritual 3 (Ask For The Failure Mode).

Lesson: the structural ritual is older than the name. Medicine has known this since Osler. Software is catching up.

Case 3: The Ariane 5 Rocket (1996)

The Ariane 5 Flight 501 self-destructed 37 seconds after launch because flight control software inherited code from Ariane 4, which had different physical constraints. Each layer of assumption was locally reasonable: the code worked on Ariane 4, Ariane 5 was similar to Ariane 4, therefore the code would work on Ariane 5. A 64-bit floating-point value representing horizontal velocity overflowed a 16-bit integer, which had been deemed unreachable under Ariane 4 dynamics.

A base-test would have asked: “On Ariane 5, does horizontal velocity ever exceed the Ariane 4 maximum?” A 10-line simulation would have revealed the overflow in minutes. Instead, the tower of “this worked before” survived into launch.

Lesson: reusable components carry their assumptions with them. Force the assumptions explicit every time the component crosses a context boundary (Ritual 5).

10. Empirical Grounding

  • Popper, K. (1959). The Logic of Scientific Discovery. The foundational source for the falsification principle. Chapter 4 formalizes the base-test: a hypothesis is scientific only if it specifies conditions under which it would be proven false. This is the master tool against fractal wrongness.
  • Beck, K. (2003). Test-Driven Development: By Example. Introduces the failure-centric approach as a working engineering discipline. “If it doesn't fail, we haven't learned anything.” Beck's TDD is Popperian falsification applied at the function level.
  • Lee, K. (origin attribution). The term “fractal wrongness” is attributed to Keunwoo Lee via online commentary. The concept formalizes what Popper called “unfalsifiable theories” — the kind that are wrong at every level of resolution.
  • Edmondson, A. (1999). Psychological Safety and Learning Behavior in Work Teams. Administrative Science Quarterly. Shows that psychological safety enables the dissent and challenge required to run Rituals 3 and 5. Without safety, nobody asks for the failure mode. Without the question, fractal wrongness survives.
  • Wason, P. (1960). On the failure to eliminate hypotheses in a conceptual task. Quarterly Journal of Experimental Psychology. The original 2-4-6 experiment showed that humans naturally seek confirmation, not falsification. The base-test protocol is a structural workaround for this cognitive default.
  • Gawande, A. (2009). The Checklist Manifesto. Documents how structural rituals prevent fractal wrongness in aviation, surgery, and construction. Checklists externalize the base-test so human memory cannot erode it.

11. Meta-Falsification

What would disprove this paper? In the spirit of The Prediction Trap §9, here are the specific conditions under which the authors would consider this paper wrong:

  • A longitudinal study showing that teams using the base-test protocol produce more bugs, not fewer, than teams using ad-hoc review.
  • Evidence that the 8-point detection checklist scores uncorrelate with actual fractal wrongness in postmortems (i.e., the checklist is just noise).
  • A case where Ritual 5 (Force Explicit Assumptions) demonstrably makes an AI output worse by inducing the AI to invent false constraints.
  • A principled argument that fractal wrongness does not exist as a distinct phenomenon — that all wrongness is either local (one bug) or structural (whole system), with no recursive middle.
  • Evidence that Scheherazade coefficient correlates with project success, not failure.

None of these falsification conditions have been met to the authors' knowledge. But none have been rigorously tested either. The honest position: this paper is a hypothesis wearing a white paper's clothes. Treat it as such. Run the base-test before trusting the tower.

12. Conclusion

Fractal wrongness is the cost of AI-assisted development without structural skepticism. The tower gets taller, the foundations get shakier, and the cost of verifying the whole structure grows with every floor. The Popperian base-test inverts the problem: one falsification at the base collapses the entire tower.

This v2 revision provides what the v1 lacked: worked examples, measurable criteria, full ritual definitions, case studies, and meta-falsification. The core insight (Kent Beck + Keunwoo Lee + Popper) is unchanged. The engineering scaffold around it is new.
